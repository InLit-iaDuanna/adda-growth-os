# ADDA Growth OS V1.0 — 完整交付方案

版本 1.0｜2026-09-22｜供甲方、交付负责人和 Codex 共用

## 1. 项目目标应从“七个 AI”改成“可核验的增长运营闭环”

甲方给出的方向是品牌内容、校园活动、会员复购和线上增长，不是库存损耗管理。本方案以增长场景为主，不延续另一条重库存产品路线。

核心目标：在不更换现有 POS 的前提下，让 ADDA 的运营人员完成品牌资料管理、三语言内容与校园活动生产、审批执行、第一方来源追踪、会员与实际订单连接、顾客声音处理和日常复盘。

产品的核心对象不是“对话”，而是活动、内容、来源、会员、订单、审批和结果。聊天是操作入口之一。首版既有操作界面，也有顾客 H5 和数据核验流程。

甲方原愿景值得保留的部分包括 ADDA 的品牌定位、六个内容栏目、校园主理人、ADDA MATE、三语言工作方式和开业阶段策略。但它尚未定义平台权限、数据来源、指标分母、实际执行和交付边界。这些是本方案补齐的部分。

本方案没有证明可以带来比其他方案更高的真实营收；它把“什么有效、如何核实、何时不能执行”变成可实现和可验收的产品能力。

## 2. 首版总 Goal

交付一个可部署的 Web 产品：已批准品牌知识 → 三语言内容/活动 → 人工复核与审批 → 授权发布或人工发布 → 独立来源链接 → 会员与券 → 现场 POS 引用 → 订单导入核验 → 分群触达 → 成熟复购和来源报告。

成功不是系统说“已为你制定增长方案”，而是店长可以找到一笔活动关联订单，知道来源证据、顾客是否可触达、内容是谁批准的、退款是否冲销，以及后续是否发生可确认的跨日再消费。

不把 200–500 种子用户、替代 3–5 人或固定增长百分比写成软件保证；这些是运营目标，需要实际验证。

## 3. 产品组成

后台十个入口：今日指挥台、Brand Brain、内容工作室、活动与校园、ADDA MATE、顾客声音、增长分析、任务与审批、集成与数据、设置与权限。
消费者端：活动/内容来源落地页、会员注册与独立营销同意、会员券展示、活动报名、推荐入口。
现场端：手机可用的券核验、POS 订单引用录入、签到和异常处理。现场端不能替代支付系统；核验失败或离线时不擅自兑现。

不同角色看到不同操作。总部/负责人看汇总、审核与预算；运营做内容、活动和触达；本地审核员确认孟语和表达；店长执行活动与处理投诉；收银员仅核验必要资料；分析员只读脱敏报表。

## 4. 七个能力如何落地

### Brand Guardian：品牌事实管理

品牌名、口号、Logo、SHAPLI、栏目、实际菜单、价格、权益和服务条款进入版本化事实库。用户给出的文本先标“甲方提供，待批准”。没有收到的产品表、色号、IP 图片和会员权益保持缺失。

每份文案注明引用的品牌版本、产品价格版本和活动条款。事实冲突、过期或未批准时不允许发布。不能只上传一堆文件就宣称 AI 已经正确理解整个品牌。

### Content Producer：完整内容包

一次任务输出目标指标、栏目、拍摄对象、开头变体、镜头顺序、英文/孟语台词与字幕、中文拍摄说明、标题、封面文字、CTA、来源链接、授权提示和拍摄清单。

这比只给三段文案更接近交付。运营可以编辑、排期和导出字幕与清单；系统知道内容最终有没有发布、链接是什么、哪个版本被批准。

首版不承诺自动拍视频、创建真实 IP 视觉或自动获得所有平台权限。素材优先使用甲方授权上传的文件；自动图片/视频生成需要单独 provider 和质量验收。

### Campus Coordinator：可执行的合作管理

组织/KOC 档案保存来源、核实日期、联系许可、负责人、合作阶段、交付约定和费用草稿。专属来源码连接活动与有效购买。

不编造达卡学生名单，不根据头像和私聊建立敏感画像，不自动对陌生学生群发。不以粉丝数量自动判定价值，而是在记录充分时比较实际合作交付、已验证购买与成本，并显示覆盖限制。

### Event Planner：从创意到执行

活动不只是一个好听名称。必须有时段、容量、负责人、预算、报名/签到方法、门店接待约束、素材/场地许可、优惠规则和成功指标。

采用约 12 个可配置模板，覆盖朋友聚会、学习交流、校园社团、摄影和新品测试等场景；涉及实际比赛、节日或校园时间表必须有核实来源。没有开业日期，不能生成具体倒计时。

### CRM Planner：会员关系与许可

ADDA MATE 从第一天建立，但会员注册和营销许可分开。必要数据包括验证后的联系方式、语言、消费与同意记录，可选学校和偏好；默认不建立性别、宗教、收入或关系网络标签。

“14 天没来”应解释为在当前可观测订单数据中没有再消费，并显示身份匹配覆盖率。系统按确定规则生成分群，再以冻结人群、批准模板、预算、安静时段和频控约束触达。

### Customer Voice：问题必须进入任务

评价/客服记录有来源、原文、时间、标签、负责人、处理时限和关闭证据。卫生/安全类问题升级人工；回复必须引用已批准事实，不自行诊断或承诺赔偿。

日报同时展示记录条数与标签次数，避免多标签总数超过评论数后制造错误报告。没有 API 时用人工登记/导入和原平台回复回填，不能声称统一接入全部私信。

### Growth Analyst：数字和建议分开

营收、订单、首购、复购、归因由代码计算。AI 只解释、提出假设和生成任务草稿。日报只给最多三项优先行动，每项有证据、目标指标、负责人、预算、期限和不应突破的条件。

任务优先级先看必须处理的风险/过期事项，再看当日已批准计划与可执行资源，不凭模型编造预计多卖多少杯。没有成本不能展示利润 ROI，没有对照不能把归因当增量。

## 5. 三语言不是三个翻译按钮

后台默认中文，支持英文操作；顾客端英语与孟语。每个公开版本从同一已批准 brief 生成，再做关键金额、日期、门店、产品和权益一致性校验。

孟语稿必须有当地审核人的确认。中文回译帮助甲方理解，但不能证明孟语自然。系统保留“模型初稿→人工修改→修改理由→批准样例”，供下一次检索参考。它比简单保存聊天历史更有用，但仍不是未经验证的品牌护城河。

## 6. 六个增长指标应这样验收

| 甲方想看的数字 | 产品显示 | 不应混淆 |
|---|---|---|
| 曝光量 | 按平台定义、期间和自然/付费分列 | 跨平台展示次数不是去重人数 |
| 到店人数 | 现场核验签到、明确计数客流、可核验线上来源买家分列 | 扫码、导航、报名不是现场到店 |
| 首单转化 | 观察期完整的新注册会员 7 天首次观测购买转化 | 不能冒充全部到店顾客转化 |
| 会员新增 | 去重注册、已验证联系与营销同意分别展示 | 注册不是营销授权 |
| 30 天复购率 | 已完成 30 天观察的首购 cohort 中跨日再购比例 | 新店第 7 天不能有成熟 30 天结果 |
| 老客带新 | 经推荐关系和首次有效订单核验的不同被邀请人 | 邀请链接点击不算新客 |

每个指标显示口径、分子分母、时间窗、完整数据截止时间和覆盖率。未知用 null 与原因，不用零掩盖。

一笔订单只能有一个主归因活动，其他触点作为证据保留。优先使用核实券/码，其次是可连接身份的合格第一方触点；无法确认的部分留 unknown。来源自报另列，不能自动包装成确定归因。

## 7. 四条必须可演示的业务闭环

第一条，内容到交易：批准品牌与活动 → 内容包 → 本地复核 → 特定版本审批 → 发布证据 → 来源链接 → 会员/券 → 收银引用 → POS 核验 → 来源报表。

第二条，校园到推荐：核实合作对象 → 合作审批 → 专属码 → 报名/现场签到 → 有效首购 → 推荐台账 → 退款和奖励审核。

第三条，会员到复购：真实消费 → 规则分群 → 联系许可 → 模板/人群审批 → 发送前重查 → 触达状态 → 后续订单 → 成熟复购；可以保留未触达对照组。

第四条，声音到改善：评论导入 → 标签和证据 → 升级/指派 → 处理与回复审批 → 回执/人工回填 → 关闭和复盘。

任一闭环中“建议生成”“已批准”“调用被接受”“实际送达/发布”“已执行”“产生结果”都应是不同状态。

## 8. 平台接入应分级

官方参考见 references/SOURCES.md。

WhatsApp：首个真渠道候选。必须有联系许可、批准模板和实际账号能力；发送前再次验证同意、模板、时段和频控。没有许可不能以导出名单让人工发送来绕过规则。

Facebook/Instagram：首版保证内容包、人工发布回填与指标导入；取得并实测账户和权限后开放相应 API。不能以一个“连接成功”按钮代表所有读、写、私信、评论与分析能力均可用。

TikTok：官方 Direct Post 限制未审核客户端，并不接受仅供内部团队上传的用途。自建单品牌工具不应把自动公开发布写成默认承诺；采用人工发布或合适的已获批服务。

Google Business Profile：当前 API 申请包含已验证且活跃 60 天以上业务档案等条件。新店实施不能预设权限已具备；不具备时保留人工流程，不抓取绕过。

POS：优先 CSV 导入+对账，后续接一家实际授权 POS。没有实时接口时清楚显示截止，不给假实时库存和销售判断。

各 connector 需要能力表、状态、检查时间和证据，区分 demo、manual、live。缺凭证可继续开发核心，不可以在验收时改成假成功。

## 9. 技术路线和参考项目

默认一套 TypeScript 模块化单体：Next.js Web/API、独立 Node worker、PostgreSQL/Prisma、pg-boss、Zod、Better Auth、AI SDK provider adapter。模型与存储可替换；环境变量配置实际可用模型。

七个技能共用数据库与审批，不做七个微服务或八个自主循环。业务计算在 domain，平台在 adapters，模型只输出经过 schema 和事实检查的草稿。

参考 Postiz 的排期和发布状态、Chatwoot 的会话/工单协作、Twenty 的关系管理、AI SDK 的类型化工具、pg-boss 的后台任务，以及 Langfuse 的运行追踪。不是把这些系统全部部署起来。

复用需要核对具体许可：Postiz README 为 AGPL-3.0；Chatwoot enterprise 和 Langfuse ee 有单独边界。方案建议先参考设计或通过独立 API 集成，不在闭源交付中随意拷贝源码。

## 10. 安全与可靠性是正式功能

批准绑定内容、受众、渠道、预算与期限；改稿或改价后旧批准失效。外发执行再次检查权限、同意、模板和限制。AI 不能批准自己的建议。

数据库和所有搜索、导出、后台任务按 tenant/store 隔离；不能只隐藏 UI。会员敏感联系字段脱敏后才进入模型上下文，日志不保存秘密和完整聊天。

核销与导入幂等；外部发送超时后先进入 unknown_delivery 并对账。不能因为用了可靠队列就宣称第三方 API 的副作用恰好发生一次。

全额退款移除资格并冲销相应结果；部分退款减金额；相同订单重导不加营收。同日购买可计订单，但本产品不把它作为跨日复购。

模型失败时台账、手工编辑、核验与基础报表仍可使用。渠道撤权立即停用，不绕过授权。所有外发默认关闭，生产上线和真实测试明确授权。

## 12. 交付与验收

DEMO_READY 仅表示合成数据演示可用。CORE_ACCEPTED 表示真实甲方数据和第一方闭环可用，真实模型与本地语言审核通过。LIVE_CHANNEL_ACCEPTED 表示合同指定渠道已实测。PRODUCTION_READY 还需要权限、安全、备份、客户配置和签字。

交付源码、锁文件、schema/迁移、导入模板、部署与回滚、环境变量示例、API 文档、品牌/技能配置、测试证据、数据导出与备份恢复、依赖许可清单、管理员与运营培训、已知限制。

合同建议将核心产品、指定渠道联调、新增功能和维护分开计价；明确模型/消息/托管费付款人。平台审核通过和运营增长不是程序员能够独立保证的事项。

甲方必须提供的资料详见 templates/CLIENT_INPUTS.md：品牌素材、真实产品与价格、店铺时间地点、会员权益、POS 样本、同意文案、平台授权、本地语言审核人和生产环境。可用示例数据开发，不能用示例数据替代这些正式确认。

## 13. 最重要的验收问题

让甲方亲自完成一次活动，从批准内容到手机扫码、门店核验、订单导入和报告；再故意改动已批准价格、重复导入订单、在消息发出前退订。

系统既要把正确的事做完，也要把错误的事挡住。

最终交付的是一套可运营、可对账、可追溯、可恢复的增长系统。七类 AI 能力只是其中的工作方式，而不是交付完成的证据。
