# G02 ExecPlan — POS 导入、身份映射与指标引擎

## 目标和用户可见结果

在 G00/G01 数据边界上交付订单事实层：运营上传订单/退款 CSV 后先预览和逐行报错，再显式提交；重复文件/订单/退款不重复入账；金额使用 minor units，退款保留事件并重述净额；报告显示 `as_of`、`complete_through`、coverage、unknown、formula version 和 provisional 状态。指标由代码从已提交订单与会员记录计算。

## 仓库现状与依赖

G00/G01 已有 JSON repository、租户/门店授权、产品价格和测试工具。运行环境无 PostgreSQL/Docker，因此本目标继续使用可替换 `file-dev` staging adapter；合成 golden fixture 仅用于离线回归，不能代表真实销售。

## 设计与文件路径

- `packages/domain/src/imports.ts`：CSV 解析、字段/金额/日期校验和行错误。
- `packages/domain/src/metric-engine.ts`：只接收授权范围内的事实，返回 MetricResult 合同字段。
- `packages/db/src/repository.ts`：staging/commit、幂等键、退款和水位持久化。
- `apps/web/src/server.ts`：`/api/imports/*`, `/api/metrics`, `/api/members`, attribution evidence。
- `tests/g02.test.ts`：重复导入、修订、错误隔离、golden 指标、时区/水位边界。
- `artifacts/G02/`：导入对账、指标 JSON 和测试输出。

## 实施步骤

1. 定义订单、退款、会员、导入批次和行错误结构，所有记录保留原始行 hash 和 tenant/store scope。
2. 实现 CSV parser（不信任客户端 header/tenant），preview 不产生营收，commit 使用幂等唯一键。
3. 对相同订单金额变更生成 correction 审计并替换当前事实；退款累计超过订单净额时隔离整行。
4. 写纯函数 metric engine，按门店时区 business date 处理跨日复购，完整水位不足时返回 provisional/null reason。
5. 将 golden fixture 通过 import API/服务导入测试 repository，比较代码计算结果与 expected_metrics。
6. 运行所有回归，保存实际证据；无完整 POS 水位时 UI 明示 provisional。

## Surprises & Discoveries

fixture 中包含重复订单和重复退款行；正确行为是去重而非静默累加。M003 同日多单不能算跨日复购，M006 注册观察窗不足不能进成熟 7 天 cohort。

## Decision Log

- D-G02-01：preview 与 commit 分离；只有 commit 后订单进入指标事实层。
- D-G02-02：相同外部订单金额变化保留 correction 链和审计，不创建第二笔销售。
- D-G02-03：`complete_through` 未覆盖观察窗时返回 provisional/null reason，不把未知当零。

## 回滚与幂等

导入批次不可变；重复 `file_hash` 返回已有预览/对账。commit 使用 `(tenant,store,source,external_order_id)` 和退款 adjustment key；纠错保留前一版本，可按批次标记取消并重算指标。
